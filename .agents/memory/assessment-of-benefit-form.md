---
name: Assessment of Benefit (AoB) document decisions
description: Non-obvious data-sourcing and content decisions for the Medicare Assessment of Benefit document generator.
---

- Referring-doctor details (name, provider number, address, referral date) shown on the AoB come from the **scan request** linked to the appointment (`getScanRequestByAppointmentId`), not the appointment's own referring-doctor fields — the appointment fields can be stale/free-text while the request is the authoritative referral record. If the request is linked to a saved Referring Doctor, that record's address/provider number take precedence.
  **Why:** explicit clinic instruction — the appointment-level referring doctor fields aren't reliably kept in sync with the actual referral.

- The form's "Practitioner Who Rendered the Service" field intentionally reuses the referring doctor's name/provider number. The app has no separate concept of a "rendering practitioner" distinct from the referrer.
  **Why:** explicit clinic instruction, not a bug — don't try to introduce a new rendering-practitioner field to "fix" this without checking with the user first.

- Equipment Number and SCP fields from the real Medicare form are deliberately omitted (not tracked anywhere in the app) rather than shown blank.

- Two document copies are generated and stored per signature: Practitioner/clinic copy and Patient copy (patient copy gets a short retain-this-copy footer, no other content difference). Both get attached to the patient file as separate documents.

- Fields that are always the same for this practice's workflow are hardcoded rather than sourced from data: "In-hospital referral: No", "Number of patients attended: 1", "Is the assignor the patient? Yes", "Agreement Type: Post-assignment".

- The document is generated by overlaying an SVG text/checkbox layer onto the two ACTUAL scanned Medicare Bulk Bill Webclaim template images (practitioner copy + patient copy), composited via `sharp` — not code-drawn from scratch. Coordinates must be calibrated against the real template pixel dimensions; visual estimation from a chat-displayed (downscaled) image is unreliable — burn in labeled gridlines (SVG overlay at 10–25px steps) and crop/zoom into each field region to verify placement before trusting it.
  **Why:** the business requirement is to reproduce the real government form exactly (for compliance/familiarity), not an approximation — an earlier code-drawn-from-scratch version was replaced for this reason.

- The two AoB template scans do NOT share a vertical layout — the patient copy is a *different photo*, not a uniform scale of the practitioner copy (`loadTemplate` only normalises WIDTH to 1754). So the services table needs PER-COPY row coordinates: `F.servicesTable.rowCentersByCopy.{practitioner,patient}` (12 rows, ~62px pitch), and `buildOverlaySvg`/`renderCopy` take a `copy: "practitioner"|"patient"` arg. SVG text baseline = row centre + `baselineOffset` (≈4px) to sit centred in each digit box.
  **Why:** the original single shared `rowYs` array put items on the header / outside the boxes on both copies (worse on the patient copy). Calibrated each copy's centres against its own digit boxes.
  **How to apply:** the horizontal columns (descX/itemX/benefitX) DID line up on both and are shared — only the vertical rows differ. The four boxed digit fields (Medicare, referral date, provider number, LSPN) AND the in-hospital "No" checkbox have SINCE been given per-copy Y too (`y: {practitioner, patient}`) after the same crop-calibration — the patient copy really is offset (e.g. patient referral-date box sat ~40px higher than practitioner). A few faint/ambiguous single-value fields (assignor Yes, post-assignment, num patients, DOB) are still shared-Y on purpose — moving them speculatively off a downscaled image risks regressions; re-check only if the user reports those specifically.

- Location Specific Practice Number (LSPN) is **per LOCATION**, not per clinic: the number identifies the PREMISES the scan was performed at, so it follows the calendar (location) the booking sits on. Every site's number is edited in one place — Clinic Setup → Locations (each row, plus the main location); it was deliberately removed from the Clinic Settings general tab, and `PUT /api/clinic/:id` no longer accepts the field (that route is any-authenticated-user, while the Locations routes are owner/admin-gated).
  **Why:** a multi-site practice bills each premises under its own LSPN; the clinic-level column now means the MAIN location's number only.
  **How to apply:** never fall back to the clinic-level number for a satellite with no LSPN recorded — print BLANK. A blank field is a clerical gap; another site's number on a Medicare document attributes the service to the wrong premises. `resolveAobLspn(clinicId, appointment)` centralises this and always returns an explicit `string | null` (it swallows lookup errors into `null`). The renderer's `opts.lspn === undefined` means "no location was resolved, use the clinic's number" and exists only for the preview script — never let a signing path leave it undefined. Exception: with no appointment AND no extra locations on the clinic, the clinic number is unambiguous and is used.

- ONE current AoB form per visit, and both sides pick it with `selectCurrentAobForm` in `shared/aob.ts`: the newest form that is signed OR has items, else the newest.
  **Why:** marking a report sonographer-complete used to unconditionally create a SECOND form for an appointment that already had one. The report-created form is always itemless (its `items` come from `req.body`, which the client never sends), and the appointment panel showed the newest form — so a signed form with real item numbers and a generated document looked like nothing had been saved for the visit. Found 2026-08-06; ~24 production appointments were already in this state.
  **How to apply:** never let server and client apply different "which form is current" rules, or the screen shows one form while the server acts on another. Sonographer-complete reuses an existing form (same clinic, and unlinked or already this report's) instead of creating one; a second study on the same booking must still get its own form, so never reuse a form that another report already claims.

- The performed-at LSPN is SNAPSHOTTED onto the AoB form at creation, and the sign step prefers that snapshot over a live lookup.
  **Why:** deleting a location moves its appointments back to the main calendar (`locationId = null`), so a form still pending signature would otherwise print the MAIN site's number for a scan done elsewhere. Same reasoning as the other snapshotted fields on this form.
  **How to apply:** a live lookup still runs when the snapshot is null, to cover forms created before the column existed.

- Any text-wrapping helper used for fixed-height form fields (e.g. service descriptions) must indicate truncation whenever it drops trailing words, even if the last kept line still has spare character width — checking "does the last line's own length exceed the limit" is not sufficient, since a line can be short while a later word still got cut. On a billing/medical form, a silently dropped word (e.g. "bilateral") is a real data-loss risk, not just a cosmetic issue.

- An AoB form is reachable by EITHER `reportId` OR `appointmentId`, and either one can be null depending on how the form was born — so neither is a universal key. Sono-complete forms always have `reportId` (appointmentId opportunistic, best-effort same-day patientId match, often null). Forms generated on demand from the calendar appointment screen always have `appointmentId` but `reportId` null (no report need exist). Any UI that surfaces the pending-signature step must query by whichever id it has, never assume one is always present.
  **Why:** found in production — pending_signature rows existed with `appointment_id` null and no way to reach them (calendar only queried by appointment); later, on-demand calendar creation added the mirror case (`report_id` null). An earlier memory claim that "reportId is always set" is FALSE since on-demand creation exists.
  **How to apply:** the data fact (either id can be null) still holds, but the SIGNING step is now **calendar-only** (see the "signing surface" entry below) — the Reporting Room no longer surfaces signing, so `reportId` no longer buys reachability for the sign step. A sono-complete form whose `appointmentId` never linked is therefore unreachable for signing until a fresh form is generated from an appointment.

- Staff can generate/regenerate an AoB form on demand from the calendar appointment dialog at any time (not gated on sono-complete), via `POST /api/appointments/:id/assessment-of-benefit`. Because this can create a SECOND pending form for one visit (e.g. regenerating to fix a mistake), the route deletes prior UNSIGNED forms for that same appointment after creating the new one (`deleteSupersededPendingAobForms`, clinic-scoped, `ne(id, newId)`). Signed forms are never deleted.
  **Why:** without superseding, a mistaken pending form left on the report card / calendar could still be signed separately, filing two signed Medicare documents for one visit.
  **How to apply:** the item-confirmation UI is the shared `AobItemsDialog` (client/src/components/aob-items-dialog.tsx), reused by both the calendar on-demand flow and the Reporting Room sono-complete flow — change item-editing behavior there once, not per-surface. It takes an optional `initialItems` prop: when present (calendar editing an existing form) it prefills those items instead of recalculating from scan types; when absent (sono-complete) it recalculates. Residual gap: a sono-complete form whose appointmentId never linked (null) is a separate lineage the appointment-scoped supersede can't catch AND (since signing is now calendar-only) can't be signed at all — staff must generate a fresh form from the appointment.

- Sonographers routinely mark a study "Sono Complete" straight from the report CARD in the Reporting Room list, never opening the report editor. So any per-report follow-up action that lives ONLY inside the editor will be effectively invisible — it must also appear on the card.
  **Why:** found in production — user completed studies from the card and reported an editor-only button "not showing"; it existed, but only in the editor they never opened.
  **How to apply:** general lesson still holds for any future per-report action — the card list has no per-report data by default, so fetch once (clinic-scoped) and build a `Map<reportId, …>` to gate the card, not an N-per-card query. NOTE: the AoB sign button specifically has since been **removed from all Reporting Room surfaces** (card + editor) — do not re-add it there; signing is calendar-only now.

- AoB signing surface = **calendar appointment dialog ONLY** (per explicit user request). The Reporting Room keeps ONLY the sono-complete item-confirmation pop-up (`AobItemsDialog` with no `initialItems`); it no longer imports/renders `AobSignDialog` or queries pending/report AoB forms. The sign dialog (`aob-sign-dialog.tsx`) is deliberately **full-screen** (`w-screen h-dvh`, no rounding) so the calendar is fully hidden when the iPad is handed to a (often older) patient. Items are editable right before signing via the calendar's "Edit item numbers"/"Generate a new form" button, which opens `AobItemsDialog` prefilled from the existing form.
  **Why:** explicit clinic workflow — item numbers originate with the sonographer but admin staff capture the signature later from the calendar, and the full-screen hand-off avoids confusing patients with the clinic UI. Use `h-dvh` not `h-screen` so iPad Safari's collapsing toolbar doesn't hide the Cancel/Sign buttons.
  **How to apply:** don't reintroduce any AoB sign entry point in Reporting Room "for convenience" — it was intentionally stripped. If a stranded appointmentId-null form needs signing, the path is: generate a fresh form from the appointment.

- Any UPDATE...returning() on the encrypted `reports` table (or any encrypted table) MUST pass the returned row through `FieldEncryption.decryptFields` before use — `sonographerCompleteReport` originally did not, so `report.patientName` came back as ciphertext and got snapshotted into the AoB form and baked (as `U2FsdGVk...`) onto the generated Medicare document. decryptFields is idempotent (only touches _encrypted/"U2FsdGVk"-prefixed values), so adding it is always safe.
  **Why:** found in production — a signed AoB doc had the encrypted blob printed where the patient name should be.
  **How to apply:** every read/return path off an encrypted table decrypts; audit any `.returning()` you add on `reports`/patient tables.

- AoB forms are created at Sono Complete but the report is often linked to its patient (and appointment) only afterwards, so the form is born with `patientId`/`appointmentId` null → signed docs can't file to the patient file and the calendar can't surface it. The signing step is the reconciliation point: re-derive patientId from the report, refresh the patient snapshot (name/DOB/Medicare) from the live decrypted patient, and link+complete the same-day open appointment, all before generating the document.
  **Why:** found in production — "started the study, signed the form, but nothing in the patient file or on the appointment."
  **How to apply:** don't rely on the linkage captured at sono-complete; heal it at sign. Claim the form atomically (conditional UPDATE `status='pending_signature'`→`signed`) so docs/patient-documents are generated exactly once, and roll back to pending (only while documentUrl IS NULL) if generation throws.

- Boxed digit fields (Medicare, referral date, provider no., LSPN) are rendered PER-GLYPH via `boxedText`: each character is its own `<text text-anchor="middle">` centred at `x = startX + i*pitch`, `y = f.y[copy]` — NOT a single letter-spaced string (letter-spacing drifts across the row and misaligns from the printed boxes). To calibrate: measure one box's centre-X for `startX`, the box-to-box gap for `pitch`, and set the baseline to box-centre + ~5px. Long values just extend right (no wrap/clip in SVG), so overflow past the last printed box is cosmetic only.
  **Why:** the earlier single-string `spacedText` visibly drifted; per-glyph centring is the only reliable way to sit each char in its own box.

- `xMark(x, y, size)` treats (x, y) as the checkbox's TOP-LEFT corner; the X strokes are drawn to centre at (x + size/2, y + size/2). SVG `<text>` `y` is the BASELINE (≈ box-centre + 5), a different convention — don't copy a checkbox's y into a text field or vice-versa. Checkboxes need per-copy Y for the same reason digit boxes do (the "In-hospital: No" X printed below its box on the patient copy until given a per-copy y).

- The rendering-practitioner (bottom-right box) resolution order is: explicit staff override (physicianId passed from the calendar's `AobItemsDialog` "Reporting doctor" dropdown) > same-day report's `physicianId` > appointment's `physicianId`. The override exists because staff often need to record who reported before any report is written/finalized (right after the scan, patient still present) — don't remove it in favor of pure auto-detection.
  **Why:** auto-detection alone (matching report/appointment) can't cover the common "patient about to leave, no report yet" case.

- Referral date on the AoB comes from `scanRequest.requestDate`, which is stored ISO `yyyy-MM-dd` (native `<input type="date">`), NOT DDMMYYYY. `referralDateDigits` must reorder ISO → DDMMYY for the six D D M M Y Y boxes; a bare 8-digit value is disambiguated by a plausible leading year (1900–2100 ⇒ YYYYMMDD, else DDMMYYYY).
  **Why:** the original code assumed DDMMYYYY, so "2026-07-04" printed as 20/26/04 — a wrong date on a government billing document. The 6 rendered digits happen to look plausible, so this is easy to miss unless you check the actual stored format.
  **How to apply:** any AoB date field sourced from app data is ISO; reorder, don't slice front-to-back.

- The "Benefit assigned" (fee) column is ALSO a boxed field on the real template, not a free-text `"$76.25"` string: 3 boxes for dollars + a printed decimal dot + 2 boxes for cents (5 boxes total), same per-glyph `text-anchor="middle"` centring as the other boxed fields. Never draw a `$` or `.` there — the template prints the dot. Dollars are right-aligned into their 3 boxes (blank-padded on the left if fewer digits); cents are always the fixed 2 digits.
  **Why:** user supplied a real-form photo showing dashed digit boxes with a built-in printed dot; the prior code drew a freeform currency string that ignored the boxes entirely.
  **How to apply — measurement method (reuse for ANY future box calibration on this file):** don't eyeball a resized/cropped preview. Normalize the template to 1754px width via sharp, read the raw grayscale buffer, sum per-column darkness over the row's y-band, and find the local peaks/clusters — those are the printed border lines; box centres are the midpoints between consecutive borders, pitch is the spacing. This found borders at ~53px pitch (practitioner) vs ~55px (patient) — confirms the two copies are genuinely different photos with slightly different scale, so box `startX`/`pitch` must be per-copy (`{practitioner, patient}`) like the other boxed fields, not shared like the plain text columns (descX/itemX).

- Column-darkness scanning breaks down for boxes whose BORDERS themselves are dashed (not solid) and that have printed "/" slash glyphs nearby — the dashes register as many small, similarly-spaced dark clusters indistinguishable from noise, and a slash's diagonal stroke pollutes columns near the pair boundary. This defeated the automated approach for the "Date of service" field (6 boxes, DD/MM/YY groups, top-right near Patient ref number).
  **Why:** dashed borders + slashes produce a near-uniform low-level darkness signal across the whole row, so peak-finding can't reliably separate real borders from noise.
  **How to apply:** when column-darkness scanning gives ambiguous/noisy results, switch to iterative visual calibration instead of forcing the automated method: overlay actual coloured single-character digits (SVG `<text>`) directly onto the normalized template at a guessed x/y, crop+zoom tightly (6-7x) around just that box or box-pair, and visually confirm the glyph sits centred between two dashed borders; adjust x and re-render until confirmed, one box (or box-pair) at a time rather than guessing the whole row at once. Also independently confirm any solid/thick divider lines (e.g. the services-table's right edge) via column-darkness scanning first — those ARE unambiguous — to get a hard right-boundary constraint before iterating.

- The "Date of service" field's 6 boxes have box-to-box pitch ≈52 within each DD/MM/YY pair, and a larger ≈62-67 gap only where the printed slash sits (between box2/3 and box4/5) — NOT the "compressed last pair near a divider" pattern an earlier calibration attempt guessed. Final calibrated centres (shared X across both copies, only Y differs): `[1379, 1431, 1498, 1550, 1612, 1664]`, fontSize 26, y `{practitioner: 174, patient: 142}`. Implemented via `boxedTextAtPositions` helper (explicit `xPositions` array) alongside the existing pitch-based `boxedText`, reusing `toDdMmYyDigits`.
  **Why / how this was actually calibrated:** the first attempt at this field used the iterative visual-overlay method but got it wrong — a low-effort visual check made it *look* plausible (digits landed in some dashed box), but the whole sequence was actually shifted one box to the right, and the two Y-digits both landed inside the last box because the guessed pitch was too tight (32px) near the end. The reliable fix came from the user hand-annotating a screenshot with red rectangles around the REAL box edges; from that, detect the red-rectangle edges by scanning pixel columns/rows for the annotation colour (`r>120&&r<220&&g<80&&b<80` worked for a dark-red marker), and separately detect the *rendered digit glyph* centres in the same screenshot (scan for the fill colour, e.g. `r<100&&g<100&&b>60&&b<180&&b>r` for `#1a1a6e` navy). Since the rendered digits were placed at KNOWN template-space X values, pairing (known template X, measured screenshot X) for all 6 digits gives an exact linear regression (screenshot_x = slope·template_x + intercept) — invert it to map any measured screenshot box-edge/centre straight back into this file's 1754px coordinate space, with no guessing required.
  **How to apply:** whenever a user annotates a rendered document with a box/line to show a misalignment, prefer this regression approach over another round of eyeballed guesses — it only requires the CURRENT (known-wrong) coordinates and the user's screenshot, and gives an exact answer in one pass instead of another iterate-and-guess cycle.

- The services table's "Item number" column is also a boxed field (5 boxes, one digit each — MBS item numbers are standard 5-digit codes), not free-text; it was originally drawn as a single left-aligned string that overflowed into/past box 1. Fixed the same regression way: paired the known template X of the ALREADY-correct description column start and the old (wrong) item free-text start against their measured positions in a user's red-box-annotated screenshot, inverted to get box centres in template space — landed on a clean uniform pitch (~53, matching the other boxed fields, unlike the date-of-service field's irregular slash-gap pitch). Rendered right-aligned/blank-padded into the 5 boxes via per-glyph `text-anchor="middle"`, same convention as the benefit-dollars boxes, applied once per row via the existing `rowCentersByCopy` loop so all 12 rows get it automatically — no special-casing row 1.
  **Why:** confirms the regression-from-annotated-screenshot method generalizes to any boxed field, not just the date field it was first used for — and that fields sharing similar box sizing here tend to share the same ~53 pitch, so a clean-pitch result is itself a good signal the regression was set up correctly.

- Not every field on this form is a digit-box grid — "Patient's full name" is actually TWO separate plain dotted lines (surname line, then first-name line), and DOB is a single plain dotted line, both meant for free/cursive handwriting-style text, not per-glyph boxed digits. Rendering `patientName` ("First Last" in this app's data) as one combined string on one line, or a raw ISO date, doesn't match the real form's layout/format.
  **Why:** found on user review — the form has a real handwriting-style dotted line per field, distinct from the boxed-digit fields (Medicare number, dates-of-service, item numbers) documented elsewhere in this file; conflating the two field styles produces a technically-present but visually-wrong value.
  **How to apply:** before assuming a field is boxed-digit, check whether the template shows individual dashed boxes (per-glyph) vs one continuous dotted line (free text) — mixing the two rendering styles up is an easy mistake since both use dotted/dashed strokes.

- The signature PNG from `aob-sign-dialog.tsx`'s canvas must never be flattened onto an opaque white fill before compositing — `ctx.fillRect` with white (done once at canvas init and again in `clear()`) bakes an opaque white rectangle into the exported PNG's alpha channel, so `sharp .composite()` draws a visible white box over the template's own printed background/lines instead of showing only the ink strokes. Use `ctx.clearRect()` and skip any `fillStyle` fill; keep the `<canvas>` element's CSS `bg-white` so it still *looks* white on-screen while signing (the drawing surface only, not the exported bitmap).
  **Why:** found on user review — the composited AoB document had an opaque white rectangle sitting over the signature line and any table gridlines beneath it.
  **How to apply:** any future canvas-based signature/drawing capture that gets composited onto a pre-printed background image must init/clear via `clearRect`, never a filled rect, or transparency silently gets lost at export time, not at composite time.

- The practitioner and patient AoB template photos are NOT just vertically offset by one constant — per-section offsets vary in sign (the header name/DOB fields land at nearly the same Y on both copies once X is fixed, but the assignor's signature/date-of-signing section near the page bottom has the patient copy's row sitting ~30-40px HIGHER than the practitioner copy's, the opposite direction from an earlier guess for that region). Don't extrapolate one region's per-copy delta onto another region of the same page — recalibrate each field group's per-copy Y independently, using the same normalize-to-1754px + gridline-overlay-crop method as other boxed fields.
  **Why:** an initial attempt reused a "patient copy is offset +N from practitioner" assumption from a different field group and got the signature/date row ~90px too low, landing on top of the footer privacy-notice paragraph instead of the signature line.
  **How to apply:** always verify a newly-calibrated per-copy Y against a cropped render of THAT specific field, even if a nearby field group's per-copy delta already looks confirmed.

- Signature `maxH` (fit-inside height cap before compositing) must be sized to the TIGHTEST available vertical gap across both copies, not just whichever copy is checked first — the patient copy's gap between the declaration paragraph and the signature line is meaningfully smaller than the practitioner copy's, so a `maxH` that looks fine on the practitioner copy can clip a tall/wavy real signature into the paragraph text above it on the patient copy. Settled on maxH 60 (down from a naive 85) as a shared safe value for both.
  **Why:** found via a synthetic tall test signature during verification — it fit cleanly under the practitioner copy's roomier gap but visibly overlapped text on the patient copy at the same maxH.
  **How to apply:** when calibrating any shared visual constraint (size caps, font sizes) that applies identically to both template copies, check it against whichever copy has the least available space, not just the one being actively edited.

- The above "avoid overlap" caution was later deliberately REVERSED by explicit clinic instruction: they want the signature ~50% bigger (maxW 300→450, maxH 60→95) AND positioned to sit directly over/through the "Assignor's signature" printed label, overlap with those words explicitly accepted as fine. `lineBottomY` (bottom edge of the signature bbox) had to be pushed to within a few px of the printed dotted line's actual row (verified ~1140-1145 abs-Y on both copies via gridline-overlay crop, NOT the ~1098 previously assumed) for the ink to actually reach the label text below the line — a lineBottomY only ~30px past the old value still left the signature floating well above the line with no visible overlap.
  **Why:** an earlier "looks fine" check of this exact line region had assumed the dotted line sat around abs-Y 1098; re-measuring with the labeled-gridline-crop method (this file's standard calibration technique) showed the real line is ~40-45px lower, right near the page's bottom edge on the practitioner copy (very little vertical margin left below it).
  **How to apply:** if a future request changes signature/label overlap again, don't trust a previously "confirmed" line-position constant without re-verifying via a fresh gridline crop — this file has already recorded one wrong assumption about this exact row.

- REVERSED (2026-07-05): "Expiry date checked" now always gets an X, not a checkmark. The `checkMark()` helper (SVG polyline tick) has been deleted entirely — `xMark()` is used for every checkbox-like field on this form now. Don't reintroduce a tick-mark helper here without fresh explicit clinic instruction; this exact field has flip-flopped once already.

- "Patient ref number" (small dashed box on the header row, left of "Date of service") is NOT the same field as "Medicare card number" (the 6-digit boxed field) even though the clinic wants the same medicare digits printed in both — it's a single plain box (not per-digit boxes), rendered as small (`fontSize: 13`) center-anchored free text at `F.patientRefNumber` (`x: 1187`, same Y baseline as `dateOfServiceBoxes` since they're on the same printed row). Value can overflow the box slightly since a full Medicare+IRN string is wider than the box.

- Agreement Type "Post-assignment" checkbox is intentionally left UNMARKED (`F.agreementPostAssignment` config + its `xMark()` call were both removed 2026-07-05, reversing the earlier "always X" default). If a future request wants it marked again, re-add both the coordinate entry and the render call — don't assume the old commented-out values are still accurate without reverifying against the template.

- Signature box position (`F.signature.x`, `F.signature.lineBottomY`) was recalibrated 2026-07-05 from a user's hand-annotated screenshot showing the exact target rectangle around "Assignor's signature" — moved right (`x: 130→210`) and the bottom edge raised slightly (`lineBottomY.practitioner: 1146→1128`, `.patient: 1155→1137`, preserving the existing +9 practitioner→patient relative offset). `maxW`/`maxH` (450/95) were explicitly left unchanged — the clinic confirmed the SIZE was already correct, only the position was off.
  **How to apply:** when a screenshot-vs-template pixel mapping is needed and the screenshot's aspect ratio doesn't cleanly match `REF_WIDTH`/template height (i.e. simple `imageWidth/1754` scaling gives inconsistent X vs Y scale factors), the fastest reliable method is NOT per-pixel regression against noisy OCR'd glyph clusters — instead, render the current code's own output via a throwaway script calling `renderAobCopy` directly (see `scripts/aob-preview.ts`) at the exact 1754×1148 template resolution, crop the same field region from that self-rendered image, and compare visually/directly against the corresponding crop of the user's screenshot (both showing the same printed template elements) to judge whether a value needs to move and by roughly how much — far less effort than exact-regression math for "final polish" positioning tweaks.

- Column/row darkness-scanning on a BLANK template (no rendered digits yet) is unreliable for finding a box's own borders when nearby label text, other row dividers, or dashed lines sit in the same scan window — it can confidently report a "border" that's actually a text baseline or an unrelated divider several boxes away. The self-rendered-output crop-compare method (see entry above) caught this: `medicareBoxes`/`assignorYes` per-copy Y values derived from raw pixel-darkness peaks on the blank template were wrong for the practitioner copy (text landed a full row off, in the adjacent DOB field), while the SAME method worked fine for the patient copy.
  **Why:** blank-template scans have no signal telling you WHICH detected dark row/column is the box you actually care about vs. some other printed element at a similar darkness level nearby — the render+crop method sidesteps this because you can literally see whether the rendered text sits inside the visible printed dashed box.
  **How to apply:** prefer gridline-overlay crops (labelled coordinate grid composited over a crop of the raw template) to visually read box edges by eye, or — best — the iterative render-actual-content-then-crop-compare method, over pure pixel-darkness peak scanning, whenever the two AoB template copies are involved. Confirmed once more (2026-07-05) that the practitioner and patient copies' per-copy Y deltas are NOT a fixed offset from field to field — `medicareBoxes` ended up needing a ~39px practitioner-vs-patient delta (280 vs 241), a different magnitude/direction than other boxed fields' deltas — recalibrate every field group's per-copy Y independently.

- `assignorYes` (the "Is the assignor the patient? Yes" checkbox) was converted from a single shared `{x, y, size}` to per-copy `{x: {practitioner, patient}, y: {practitioner, patient}, size}`, matching the pattern used by the other checkboxes/boxed fields — the render call must index `.x[copy]`/`.y[copy]`. Final values: `x: {practitioner: 262, patient: 242}, y: {practitioner: 923, patient: 939}, size: 24` (up from `size: 18`, made slightly bigger per clinic request alongside the Medicare digit font-size bump).

- "Patient ref number" is the Medicare card's Individual Reference Number (IRN) — the single digit printed beside the patient's name on the card, distinguishing family members sharing one card (`patients.medicareIrn`, `varchar(2)`) — NOT the 10-digit Medicare card number concatenated with it. An earlier version of this field wrongly printed `medicareNumber + medicareIrn` combined; the field is meant to show the IRN alone.
  **Why:** found on user review with a real patient whose IRN is "1" — the field showed an 9-digit run instead of just "1".

- The services table must list items in DESCENDING benefit-assigned order (highest `feeCents` first), matching the same order the Multiple Services Rule multiplier (100%/60%/50%) is calculated in — Medicare's own form convention. `renderAobCopy` now sorts a shallow copy of `aobForm.items` by `feeCents` descending immediately before rendering the table, rather than trusting whatever order the items array was saved/edited in.
  **Why:** found on user review comparing a real completed form — items were saved/displayed in the order they were added/edited (which can be arbitrary), not benefit order.
  **How to apply:** the sort happens purely at render time (doesn't mutate/reorder the stored `items` on the AoB form row or the item-editing UI) — if item order ever needs to matter elsewhere (e.g. a future printed summary), sort by `feeCents` there too rather than assuming storage order is already correct.

- Referral date rendering/sourcing were both already correct, but the field can still print BLANK in production when an appointment has no linked scan request at all (walk-in booking, or a referral that arrived by fax/paper and was never run through the electronic Scan Request import) — `referralDate` simply stays `undefined` with nothing to fall back to. Added `appointments.referralDate` (plain date column, editable in the calendar booking form's "Referring Doctor" section) as a second data source: both AoB-creation code paths now seed `referralDate` from the appointment field first, then let the linked scan request's `requestDate` override it if one exists.
  **Why:** confirmed via the existing "authoritative referral record" sourcing logic that a scan-request lookup returning nothing leaves the variable permanently unset — there was no fallback data source at all for referrals captured outside the Scan Requests feature.
  **How to apply:** if a future report shows this field still blank, check whether the appointment itself has `referralDate` set (staff need to fill it manually when there's no electronic scan request) before assuming a rendering bug — the boxed-digit rendering code itself has been correct since it was first calibrated.

- Referring doctor NAME (not just referral date) can also render BLANK on a regenerated AoB even though it showed correctly the first time. Appointments created from a scan request (via the calendar's "Schedule" button on a scan request, or a referrer-portal self-booking) never had `referringDoctorName`/`referringDoctorProviderNumber` copied onto the `appointments` row itself — AoB generation did a *live* join to the originating scan request every time, so once that scan request was archived/deleted/unlinked, the referring doctor silently disappeared with no error, since the fallback (`appointment.referringDoctorName`) was empty too.
  **Why:** confirmed via a production DB query (dev DB had no real AoB data) — found an appointment whose AoB showed the correct referring doctor (via the live join) while the appointment's own `referring_doctor_name` column was blank.
  **How to apply:** any appointment-creation path must snapshot referring-doctor fields onto the appointment at creation time, not rely solely on a later live scan-request join. Both AoB-generation code paths (sono-complete snapshot + on-demand calendar generation) now also self-heal: if a scan request is found and the appointment's own `referringDoctorName` is empty, they fire-and-forget `storage.updateAppointment(...)` to backfill it, so pre-existing appointments repair themselves the first time an AoB is generated for them.
