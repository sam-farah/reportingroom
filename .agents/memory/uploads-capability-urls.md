---
name: Uploads served as unauthenticated capability URLs
description: Why /uploads/:filename has no auth and how PHI files are protected app-wide
---

All uploaded files (worksheets, consent PDFs, signatures, logos, scan-request
source PDFs) are served by a single `app.use('/uploads', ...)` handler in
server/routes.ts with **no auth/clinic-scoping** — disk first, file_blobs DB
fallback, restore-to-disk on serve.

Protection model: filenames are high-entropy capability URLs
(ms-timestamp + per-process counter + 8 random bytes, generated by the multer
diskStorage filename fn). Knowing the URL = access; they are not guessable and
not enumerable.

**Why:** This is a deliberate, app-wide convention, not an oversight. Worksheets
(which contain at least as much PHI as referrals) use the same path. Any
"broken access control" review finding against /uploads applies to the whole
app, not one feature.

**How to apply:** Do NOT piecemeal-fix one file type by routing it through an
authenticated `/api/.../source-file` endpoint — it's inconsistent and, for
prefill-before-save flows (e.g. scan-request PDF import), there's no owning row
id yet to scope against. If real PHI hardening is wanted, change the convention
globally (auth middleware on /uploads + per-file clinic association) as its own
scoped task. `saveFileToDB` is intentionally best-effort/void everywhere; the
original is kept on disk + DB backup + startup backfill.
