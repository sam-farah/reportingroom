# Assessment of Benefits (AoB) — Medicare claim confirmation + patient signature

Status: COMPLETE. Two decoupled steps.

## Step 1 (blocking, at study completion)
When a sonographer clicks "Sono Complete" / "Mark Sono Complete" in Reporting Room, a confirmation dialog (prefilled via `calculateVisitBilling` from the report's `studyType`) shows the suggested Medicare item numbers, descriptions, and fees, editable line-by-line (add/remove items, edit fee) before the study can be marked complete — `POST /api/reports/:id/sonographer-complete` now requires a non-empty `items` array and 400s otherwise. On success it snapshots patient/physician/referrer details plus the confirmed items into a new `assessment_of_benefit_forms` row (status `pending_signature`) and auto-completes the matching same-day appointment if one is found. Referring-doctor details (name, provider number, practice address, referral date) are sourced from the scan request linked to the appointment (via `getScanRequestByAppointmentId`), not the appointment's own referring-doctor fields, and fall back to the saved Referring Doctor record for provider number/address when the request is linked to one.

## Reporting doctor chosen up-front
Rather than only being picked at report generation/finalization, the reporting physician is now set on the appointment right after verbal consent in the calendar sonographer flow (a "Reporting Doctor" step between Verbal Consent and Begin Study; skipped if the appointment already has one). This appointment `physicianId` then flows through to the report (inherited on generate/draft-create, same pattern as sonographer/consent inheritance) and is what actually appears on the AoB form's rendering-physician field, since that form is generated at Sono Complete — before the old report-time doctor pick would have run.

## Step 2 (later, decoupled)
The patient signature is captured separately — often by admin staff, not the sonographer — from the calendar appointment detail dialog. A "Complete Assessment of Benefits form" button appears there whenever a `pending_signature` AoB form exists for that appointment (`GET /api/appointments/:id/assessment-of-benefit`); it opens a signature-pad dialog (same canvas/pointer-event pattern as the kiosk consent capture) showing the confirmed items/total, and submitting calls `POST /api/assessment-of-benefit/:id/sign` with the signature PNG data URL, which generates the signed documents and flips the form to `status: "signed"`. The signature-pad dialog is a shared component (`client/src/components/aob-sign-dialog.tsx`, `AobSignDialog`), reused on both the calendar and the report itself (see fallback below).

## Fallback surface — sign directly from the report
The appointment-linking match (same-day patientId → appointment) can fail — no same-day booking existed yet when Sono Complete was clicked, or the report has no linked patient at all — leaving the AoB form's `appointmentId` null and the form otherwise permanently unreachable, since the calendar only looks up forms by `appointmentId`. Every AoB form always has a `reportId`, so Reporting Room also fetches the form via `GET /api/reports/:id/assessment-of-benefit` and shows the same "Complete Assessment of Benefits form" button directly on a sonographer-complete report when its form is still `pending_signature`. Because studies are usually marked "Sono Complete" straight from the report CARD in the list (never opening the editor), the sign button also appears on the card itself: Reporting Room fetches all pending forms once via `GET /api/assessment-of-benefit/pending` (clinic-scoped, `storage.getPendingAssessmentOfBenefitFormsByClinic`), builds a `reportId → form` map, and renders the button on any sono-complete card whose form is still `pending_signature`. The shared `AobSignDialog` is reused on all three surfaces (calendar, report editor, report card).

## Document generation
Documents are generated by overlaying confirmed data directly onto the two ACTUAL scanned Medicare Bulk Bill Webclaim form images (`server/assets/aob-templates/practitioner-copy.png` and `patient-copy.png`), not code-drawn from scratch. `server/aob-form.ts` exports `generateAssessmentOfBenefitDocument()`, which composites an SVG text/checkbox layer (pixel-calibrated coordinate map `F`, referenced against a 1754×1148 canvas) onto each template via `sharp`. Fields: Patient Details, Referral Details (incl. LSPN if the clinic has one set, "In-hospital referral: No" and "Number of patients attended: 1" as fixed defaults since they're always true for this workflow), Practitioner Who Rendered the Service (uses the report's own physician — `physicianName`/`physicianProviderNumber`, snapshotted onto the AoB form at creation — since that's the doctor who actually performed/signed off the scan; falls back to the referring doctor's details only if the report has no physician recorded), Services table (description text wraps up to 2 lines with an ellipsis if truncated, so long descriptions never silently drop clinically/billing-significant words like "bilateral"), and an Assignment of Benefit declaration + signature block. Equipment Number and SCP are intentionally left blank (not tracked by the app). The form also has a boxed "Date of service, imaging procedure or first specimen collection (DD MM YY)" field (top-right, near Patient ref number) — 6 digit boxes, sourced from the matched appointment's date, rendered with the same per-glyph box-centring pattern as the other boxed fields. Two copies are generated per signature — Practitioner/clinic copy and Patient copy — both attached to the patient file as separate documents.

## Data model
`assessment_of_benefit_forms` table (clinic/appointment/report/patient-scoped snapshot, incl. `patientDateOfBirth`, `referringDoctorAddress`, `referralDate`, `patientDocumentUrl`); `physicians.providerNumber`, `appointments.referringDoctorProviderNumber`, and `clinics.locationSpecificPracticeNumber` (editable in Admin → Clinic Settings) support the fields shown on the form. Storage CRUD in `server/storage.ts`; routes in `server/routes.ts`; document generation (image overlay) in `server/aob-form.ts`.
